# Разбор трёх семейств скиллов

Три самые популярные коллекции скиллов: **[obra/superpowers](https://github.com/obra/superpowers)** (284k⭐), **[mattpocock/skills](https://github.com/mattpocock/skills)** (258k⭐) и **[affaan-m/ECC](https://github.com/affaan-m/ECC)** (255k⭐). Их регулярно ставят рядом в подборках, будто это три варианта одного и того же. Это не так: у них разные ответы на вопрос «кому принадлежит процесс разработки» — и, как следствие, разная цена ошибки при выборе.

Данные и цифры — на 2026-09-10, по содержимому репозиториев, а не по описаниям в подборках.

## obra/superpowers — методология, которая владеет процессом

**[obra/superpowers](https://github.com/obra/superpowers)** — 284k⭐, MIT. Автор — [Jesse Vincent](https://blog.fsck.com), сейчас развивается командой Prime Radiant; есть коммерческая поддержка для enterprise.

Формулировка автора: «полная методология разработки для твоих кодовых агентов, построенная на композируемых скиллах и начальных инструкциях, которые заставляют агента ими пользоваться». Ударение — на второй половине. Скиллы не ждут, пока ты их позовёшь: `using-superpowers` встраивается в старт сессии и требует проверять наличие подходящего скилла **до любого ответа**, включая уточняющие вопросы.

### Ровно 14 скиллов

Вопреки описаниям «20+ скиллов», которые кочуют по подборкам, в репозитории их четырнадцать. Зато каждый тянет за собой справочники и техники (всего 51 файл), а ценность — в связности: они вызывают друг друга и образуют цепочку.

**Тестирование**

- `test-driven-development` — цикл RED-GREEN-REFACTOR со справочником анти-паттернов тестирования. Код, написанный до теста, удаляется.

**Отладка**

- `systematic-debugging` — четырёхфазный поиск корневой причины (внутри: root-cause-tracing, defense-in-depth, condition-based-waiting).
- `verification-before-completion` — запрет объявлять работу готовой без прогона проверок. Девиз: доказательства раньше утверждений.

**Совместная работа**

- `brainstorming` — сократический разбор задумки **до** кода: вопросы, альтернативы, дизайн по частям.
- `writing-plans` — план из задач по 2–5 минут, с точными путями к файлам и шагами проверки. Критерий: план должен быть понятен «восторженному джуну без вкуса, без контекста и с отвращением к тестам».
- `executing-plans` — выполнение батчами с чекпоинтами для человека.
- `subagent-driven-development` — свежий субагент на каждую задачу, двухстадийное ревью (сначала соответствие спеке, потом качество кода).
- `dispatching-parallel-agents` — параллельные субагенты на независимых задачах.
- `requesting-code-review` / `receiving-code-review` — запрос ревью и, отдельно, **как принимать** фидбек: с технической строгостью и проверкой, а не показным согласием.
- `using-git-worktrees` — изолированное рабочее пространство под фичу.
- `finishing-a-development-branch` — решение, что делать с готовой веткой: merge, PR, оставить, выбросить.

**Мета**

- `writing-skills` — как писать и тестировать собственные скиллы.
- `using-superpowers` — введение в систему; тот самый скилл, который заставляет агента искать остальные.

### Базовый маршрут

Скиллы срабатывают по цепочке, и это ровно та последовательность, которую система навязывает:

1. `brainstorming` — до кода вытрясти спеку через вопросы, сохранить документ дизайна.
2. `using-git-worktrees` — изолированная ветка, установка проекта, зелёный базовый прогон тестов.
3. `writing-plans` — разбивка на задачи по 2–5 минут.
4. `subagent-driven-development` / `executing-plans` — исполнение с ревью после каждой задачи.
5. `test-driven-development` — RED-GREEN-REFACTOR внутри каждой задачи.
6. `requesting-code-review` — ревью между задачами; критичные находки блокируют движение дальше.
7. `finishing-a-development-branch` — проверка тестов, выбор способа интеграции, уборка worktree.

Автор обещает, что агент так работает автономно «пару часов, не отклоняясь от плана».

### Установка

Главное изменение, которое ещё не разошлось по подборкам: **superpowers теперь в официальном маркетплейсе Anthropic**.

```bash
/plugin install superpowers@claude-plugins-official
```

Собственный маркетплейс никуда не делся и содержит ещё девять плагинов, которых в официальном нет:

| Плагин | Что делает |
|---|---|
| `superpowers-chrome` | Прямой доступ к Chrome DevTools Protocol через скилл `browsing` |
| `superpowers-lab` | Экспериментальное: автоматизация tmux для интерактивных CLI, обнаружение MCP-серверов |
| `claude-session-driver` | Запуск и управление другими сессиями Claude Code как воркерами через tmux |
| `episodic-memory` | Семантический поиск по прошлым разговорам Claude Code и Codex |
| `private-journal-mcp` | MCP-сервер приватного журнала с семантическим поиском |
| `elements-of-style` | Руководство по письму на основе Странка (1918) |
| `double-shot-latte` | Убирает переспросы «продолжить?» — сам решает, надо ли продолжать |

```bash
claude plugin marketplace add obra/superpowers-marketplace
```

Установка есть под 14 харнессов — Claude Code, Antigravity, Codex (App и CLI), Cursor, Devin CLI, Factory Droid, Gemini CLI, GitHub Copilot CLI, Grok Build CLI, Kimi Code, OpenCode, Pi, Hermes Agent. Ставить надо отдельно под каждый.

### Кому подходит

**Берите**, если процесса нет вообще и хочется, чтобы он появился сам: система принесёт TDD, планирование и ревью без вашего участия в их настройке. Хорошо ложится на соло-разработку и на команды, которым нужен единый обязательный маршрут.

**Не берите**, если у вас уже есть свой отлаженный процесс. Спорить с superpowers дорого: скиллы срабатывают автоматически, а `using-superpowers` прямым текстом запрещает агенту рационализировать отказ от них. Либо вы принимаете маршрут целиком, либо начинаете выдирать куски — и тогда теряется связность, ради которой всё и затевалось.

## mattpocock/skills — маленькие детали, которыми владеешь ты

**[mattpocock/skills](https://github.com/mattpocock/skills)** — 258k⭐, MIT. Автор — [Matt Pocock](https://www.aihero.dev), известный по Total TypeScript. Подзаголовок репозитория: «Skills For Real Engineers. Straight from my .agents directory» — то есть это не продукт, а выложенный рабочий инструментарий.

Философия сформулирована как **прямая полемика** с подходом предыдущего семейства:

> Подходы вроде GSD, BMAD и Spec-Kit пытаются помочь, забирая процесс себе. Но делая так, они отнимают у тебя контроль и превращают баги в процессе в трудноразрешимые.

Отсюда три требования к каждому скиллу: маленький, легко адаптируемый, композируемый. Работают с любой моделью. «Ковыряйся в них. Сделай их своими».

### 37 скиллов по четырём папкам

**`engineering/` (18)** — ядро инженерного цикла:

- `research` — разбор вопроса по первоисточникам с высоким доверием, результат — Markdown-файл.
- `grill-with-docs` — безжалостное интервью, затачивающее план, попутно рождающее ADR и глоссарий. Один из самых устанавливаемых скиллов вообще.
- `codebase-design` — общий словарь для проектирования «глубоких модулей»: много поведения за узким интерфейсом.
- `domain-modeling` — построение и заточка доменной модели проекта.
- `tdd` — тесты вперёд, red-green-refactor.
- `implement` / `to-spec` / `to-tickets` — превращение разговора в спеку, спеки в тикеты, тикетов в код.
- `code-review` — ревью диффа от заданной точки по двум осям сразу: стандарты репозитория и соответствие исходной задаче.
- `diagnosing-bugs` — цикл диагностики трудных багов и просадок производительности.
- `triage` — конечный автомат по ролям для разбора issues и внешних PR.
- `wayfinder` — планирование куска работы, который не влезает в одну сессию агента: карта решений на трекере.
- `improve-codebase-architecture` — скан кодовой базы на возможности «углубления» модулей с HTML-отчётом.
- `prototype` — одноразовый прототип ради ответа на один вопрос дизайна.
- `resolving-merge-conflicts`, `wizard` (генератор bash-визарда для шагов, которые может сделать только человек), `ask-matt` (роутер по остальным скиллам), `setup-matt-pocock-skills`.

**`productivity/` (7)** — работа с мышлением и передачей контекста:

- `grilling` / `grill-me` — стресс-тест плана или решения через безжалостные вопросы.
- `handoff` — сжатие текущего разговора в документ передачи для другого агента.
- `writing-for-agents` — как писать документы для агентов: скиллы, `AGENTS.md`, `CLAUDE.md`.
- `teach` — объяснить тебе новый навык или концепцию прямо в рабочем пространстве.
- `to-questionnaire` — превратить решение, которое ты не можешь принять сам, в анкету для другого человека.
- `wait-what` — «стоп, последнее сообщение не зашло: переформулируй».

**`misc/` (4)** — точечное: `git-guardrails-claude-code` (хук, блокирующий `git push`, `reset --hard`, `clean`, `branch -D` **до** выполнения), `setup-pre-commit`, `migrate-to-shoehorn`, `scaffold-exercises`.

**`in-progress/` (8)** — честно помеченная незавершёнка: `claude-handoff`, `retro`, `implement-spec`, `loop-me`, `setup-ts-deep-modules` и три скилла про письмо (`writing-fragments`, `writing-shape`, `writing-beats`).

### Две модели установки — и это важный выбор

Автор специально разводит их как две философии, и предупреждает: поставить обе — значит получить каждый скилл дважды.

**Плагин** — подписка. Весь набор приезжает как управляемый read-only бандл и обновляется, когда автор выкатывает новое:

```bash
/plugin install mattpocock-skills
```

Он тоже в официальном маркетплейсе Claude Code, добавлять ничего не нужно.

**skills.sh** — форк. Копирует редактируемые файлы скиллов прямо в проект, они становятся твоими; ничего не меняется за спиной, обновления подтягиваешь сам через `npx skills update`:

```bash
npx skills@latest add mattpocock/skills
```

Второй путь — ровно то, ради чего эти скиллы и написаны маленькими. Если планируешь править под себя, бери его.

### Обязательный шаг настройки

После установки один раз на репозиторий:

```
/setup-matt-pocock-skills
```

Скилл спросит, какой трекер задач используешь (GitHub, Linear или локальные файлы), какими метками размечаешь тикеты при триаже (их использует `/triage`) и куда складывать создаваемые документы. Без этого шага часть скиллов не знает, куда писать результат.

### Кому подходит

**Берите**, если процесс у вас уже есть и нужны не рельсы, а отдельные качественные детали: заточить план допросом, разобрать баг, сделать ревью по двум осям, передать контекст другому агенту. Отдельная ценность — скиллы про мышление и передачу, которых в двух других семействах почти нет.

**Не берите**, если ждёте, что оно само выстроит вам порядок работы. Не выстроит и не пытается: скиллы вызываются вручную, а `ask-matt` — это роутер, а не диспетчер.

## affaan-m/ECC — операционная система харнесса

**[affaan-m/ECC](https://github.com/affaan-m/ECC)** — 255k⭐, MIT, автор Affaan Mustafa. Self-description: «система оптимизации производительности агентского харнесса». По сути — самый большой из существующих сборников, который пытается закрыть всё сразу.

**Есть [русская документация](https://github.com/affaan-m/ECC/blob/main/docs/ru/README.md)** — редкость для проектов такого размера.

### Масштаб

| Компонент | Штук |
|---|---|
| Скиллы | 286 |
| Агенты | 68 |
| Legacy-шимы команд | 94 |
| Правила по языкам | common + TypeScript, Python, Go, Swift, PHP, ArkTS |

Тематический разброс скиллов виден по одному только началу алфавита: `accessibility`, `agent-eval`, `agent-payment-x402`, `android-clean-architecture`, `angular-developer`, `api-design`, `architecture-decision-records`, `benchmark-methodology`, `blender-motion-state-inspection`, `brand-voice`, `browser-qa`. Это не библиотека под один процесс, а попытка покрыть все домены.

> ⚠️ У проекта много неофициальных зеркал. Автор просит ставить только из проверенных каналов: сам репозиторий, npm-пакеты `ecc-universal` и `ecc-agentshield`, GitHub App `ecc-tools`, слаг плагина `ecc@ecc` и сайт [ecc.tools](https://ecc.tools). Сторонние перезаливы не проверяются и могут содержать вредонос.

### Пять примитивов, и один из них уникальный

ECC жёстко разделяет роли — именно это позволяет ему не вываливать всё в каждую сессию:

| Примитив | Задача | Поведение с контекстом |
|---|---|---|
| Скиллы | Переиспользуемые workflow (TDD, security review, deep research) | Грузятся, когда нужны задаче |
| Агенты | Работники с собственным контекстом и правами на тулы | Изолируют планирование, реализацию и ревью |
| Правила | Долговечные стандарты проекта или языка | **Всегда в контексте** — ставить выборочно |
| Хуки | Скрипты на события харнесса | Работают вне контекста модели |
| **Инстинкты** | Паттерны, выученные из реальных сессий, с оценкой уверенности | Вспоминаются, когда релевантны |

Инстинкты — то, чего нет у двух других семейств. Система наблюдает за твоими сессиями и накапливает паттерны:

```bash
/instinct-status        # показать выученные инстинкты с уверенностью
/instinct-export        # выгрузить свои, чтобы поделиться
/instinct-import <file> # импортировать чужие
/evolve                 # кластеризовать родственные инстинкты в скилл
/prune                  # удалить протухшие
```

`/evolve` — самая любопытная идея во всём наборе: накопленные наблюдения свёртываются в новый скилл, то есть система дописывает саму себя.

### Memory Vault — память между харнессами

Общий локальный формат Markdown (`ecc.memory.v1`) для контекста и передач между Claude, Codex, Hermes, OpenClaw, Kimi и другими. Проектные и командные памяти живут в `.ecc/memory/`, пользовательские — в `~/.ecc/memory/`.

```bash
npm install -g ecc-universal
ecc memory init --scope project
ecc memory handoff --from hermes --target codex --title "Continue auth migration" --body-file ./handoff.md
ecc memory search "authentication migration" --target-harness codex
ecc memory doctor
```

Отдельно стоит отметить **границы доверия**, прописанные в документации явно: память — это непроверенный контекст, а не исполняемая политика. Агент обязан проверять важные утверждения по авторитетным источникам и никогда не трактовать содержимое памяти как инструкцию. Проектные памяти защищены fail-closed `.gitignore`; тела памяти принимаются только через `--stdin` или `--body-file`, но не аргументом командной строки. Для такого класса инструментов это заметно более взрослый подход к безопасности, чем обычно.

### AgentShield

Сканер, который смотрит на **сам харнесс как на поверхность атаки**: промпты, хуки, конфигурация MCP, права, секреты, файлы агентов. Запускается через `/security-scan`, по заявлению автора — 102 правила и 1282 теста. Идея верная: конфигурация агента по умолчанию считается доверенной, хотя ей быть доверенной неоткуда.

### Установка: строго одна дорожка на харнесс

```bash
npx ecc-universal setup
```

Требуется Node.js 18+, Git и Claude Code 2.1+. Альтернатива — нативные команды плагина внутри Claude Code (`/plugin marketplace add https://github.com/affaan-m/ECC`).

**Не комбинируй способы установки.** Дважды установленный в один харнесс ECC дублирует скиллы, команды, хуки и конфигурацию. При этом поставить его в несколько разных харнессов — нормально. Если уже наслоилось, в README есть раздел про полный сброс.

### Цена: контекст

Главный риск ECC — не качество компонентов, а их количество. Правила всегда в контексте, а скиллов почти три сотни. В самом репозитории на этот счёт есть внятные советы, и они полезны сами по себе, независимо от ECC:

- держать меньше 10 MCP на проект и меньше 80 активных тулов — иначе окно в 200k усыхает до ~70k;
- `/context-budget` — посмотреть, что съедает бюджет, и выкинуть ненужные правила;
- скилл `strategic-compact` предлагает `/compact` в логических точках (после ресёрча перед реализацией, после вехи, после провалившегося подхода), а не по факту упора в 95% контекста — и прямо запрещает компактить посреди реализации, когда потеряются пути к файлам и частичное состояние;
- Agent Teams плодят по контекстному окну на тиммейта; для последовательных задач субагенты дешевле.

⚠️ Одно место в их гайде по экономии устарело. ECC советует прописать `MAX_THINKING_TOKENS: 10000` в настройки — но [статья Anthropic от 8 сентября 2026](./tips-ru.md#anthropic--снижение-стоимости-без-потери-качества--8-сентября-2026) относит ручные thinking-бюджеты к устаревшей конфигурации: настройки, написанные под прошлое поколение моделей, новые модели могут просто отвергнуть с ошибкой. На их же замере снятая thinking-настройка заставляла API отвергать **каждый** запрос на роутинг. Управляйте усилием через `effort`, а не через ручной бюджет токенов.

### Кому подходит

**Берите**, если нужен готовый ответ на редкий домен (ArkTS, x402-платежи агентов, инспекция состояний в Blender) или интересны инстинкты и кросс-харнессная память — таких механик больше нет нигде. Хорошо для тех, кто работает сразу в нескольких харнессах и хочет носить контекст между ними.

**Не берите**, если у вас один харнесс и обычный веб-стек. За полноту охвата вы платите настройкой и контекстом, а 90% из 286 скиллов вам никогда не понадобятся. Начинать в этом случае лучше с малого набора и дополнять по необходимости.

## Что выбрать

Короткий ответ по ситуации:

- **Процесса нет, хочу чтобы появился** → superpowers. Примет решения за вас, спорить не придётся.
- **Процесс есть, нужны детали** → mattpocock/skills, установка через `npx skills` чтобы править под себя.
- **Нужна экзотика, инстинкты или память между харнессами** → ECC, но осознанно и выборочно.

**Можно ли ставить вместе.** Технически да, MIT у всех трёх. Практически — superpowers и ECC вдвоём конфликтуют по смыслу: оба навязывают маршрут и оба тянут TDD-цикл, ревью и планирование, только по-разному. Выберите один из этих двух как основу. Скиллы Matt Pocock уживаются с любым из них, потому что не претендуют на процесс: они вызываются вручную и делают ровно одну вещь.

И общее правило, которое перевешивает выбор семейства: каждый скилл съедает 3–5K токенов на bootstrap. Ставить всё подряд «на всякий случай» — самый дорогой способ ухудшить себе работу.
