## Boris Cherny — 6 советов по Opus 4.7 · 16 апреля 2026

**Источник:** [тред в X от 16 апреля 2026](https://x.com/bcherny) — после нескольких недель работы с Opus 4.7 в режиме обкатки.

### 1. Auto mode — конец permission-промптам

Opus 4.7 любит длинные комплексные задачи: глубокий ресёрч, рефакторинг, сборку сложных фич, итерации до сходимости бенчмарка. Раньше выбор был такой: либо сидеть рядом и одобрять каждый шаг, либо включать `--dangerously-skip-permissions` и надеяться.

Anthropic выкатил **auto mode** как безопасную альтернативу. Permission-промпты уходят на классификатор-модель, которая решает:

- безопасно — авто-одобрить;
- рискованно — поставить на паузу и спросить.

Это значит, что нянчиться с моделью больше не надо. И как следствие можно держать несколько Claude в работе одновременно: пока текущий идёт сам, можно переключиться на следующий.

Auto mode доступен для Opus 4.7 на тарифах Max, Teams и Enterprise. **Shift+Tab** в CLI переключает `Ask permissions` → `Plan mode` → `Auto mode`; в Desktop и VS Code режим выбирается из дропдауна.

### 2. Новый скилл `/fewer-permission-prompts`

Anthropic выпустил скилл `/fewer-permission-prompts`. Он сканирует историю сессий, находит безопасные bash- и MCP-команды, которые регулярно просят подтверждения, и предлагает добавить их в allowlist в `permissions`.

Удобно, чтобы прибраться в permissions — особенно если auto mode не используешь.

### 3. Recaps

На этой неделе под Opus 4.7 в Claude Code включили **recaps** — короткие сводки того, что агент сделал и что дальше.

Особенно полезно, когда возвращаешься к долгой сессии через минуты или часы:

```
* Cogitated for 6m 27s

* recap: Fixing the post-submit transcript shift bug. The styling-flash
  part is shipped as PR #29869 (auto-merge on, posted to stamps). Next:
  I need a screen recording of the remaining horizontal rewrap on `cc -c`
  to target that separate cause. (disable recaps in /config)
```

Отключить можно в `/config`.

### 4. Focus mode

Boris сейчас активно пользуется новым **focus mode** в CLI — режим прячет всю промежуточную работу и оставляет только финальный результат. Модель дошла до уровня, когда ей можно доверять выбор команд и правок: смотришь только на итог.

Включить/выключить — `/focus`.

### 5. Настраивай уровень effort

В Opus 4.7 вместо лимитов на размышление работает **adaptive thinking**. Чтобы заставить модель думать больше или меньше, крути effort.

- **Low effort** — быстрее, меньше токенов.
- **High effort** — максимум интеллекта и качества.

Слайдер показывает пять уровней: `low` · `medium` · `high` · `xhigh` · `max` — слева скорость, справа интеллект.

### 6. Дай Claude способ верифицировать работу

И последнее: убедись, что у Claude есть способ проверить результат. Это всегда было важно, а с 4.7 — особенно: модель выдаёт в 2–3 раза больше, и без верификации легко набрать ворох правдоподобно выглядящего, но нерабочего кода.

Способ верификации зависит от задачи:

- **Бэкенд** — пусть Claude запускает твой сервер/сервис и тестирует end-to-end.
- **Фронтенд** — [Claude Chromium extension](https://code.claude.com/docs/en/chrome) даёт Claude управлять браузером.
- **Десктоп** — Computer Use.

Промпты Boris сейчас выглядят так: `Claude do blah blah /go`, где `/go` — скилл, который:

1. Тестирует результат end-to-end через bash, браузер или Computer Use.
2. Прогоняет `/simplify`.
3. Открывает PR.

Для долгих задач это особенно ценно — возвращаешься, и сразу видишь: код работает.

## Thariq — Управление сессиями и 1M-контекст · 16 апреля 2026

**Источник:** [гайд Thariq от 16 апреля 2026](https://x.com/trq212) — про сессии, контекст-окно и компакцию в Claude Code.

### Контекст

С контекстом в 1M токенов Claude Code тянет более длинные задачи надёжнее — но и риск засорить контекст вырос. Управление сессиями теперь важнее, чем раньше: когда стартовать чистую сессию, когда сделать compact, когда rewind, а когда делегировать субагенту.

### Короткий primer: контекст, компакция, context rot

**Контекст-окно** — это всё, что модель «видит» одним куском, генерируя следующий ответ: системный промпт, история разговора, каждый tool-call и его вывод, каждый прочитанный файл. У Claude Code контекст-окно — **миллион токенов**.

За использование контекста есть небольшой штраф — **context rot**. Качество модели падает по мере роста контекста: внимание размазывается по большему числу токенов, старое и нерелевантное начинает отвлекать от текущей задачи. Для 1M-модели заметная деградация ловится где-то около **300–400K токенов**, но это сильно зависит от задачи — не жёсткое правило.

Контекст-окно — жёсткий предел. На подходе к нему задачу нужно суммировать и продолжить в новом окне — это и есть **компакция**. Можно вызывать вручную.

### Каждый ход — точка ветвления

Когда Claude закончил ход, у тебя удивительно много вариантов, что делать дальше:

- **Continue** — следующее сообщение в той же сессии.
- **/rewind** (или двойной Esc) — прыгнуть к предыдущему сообщению и попробовать оттуда заново.
- **/clear** — новая сессия, обычно с кратким брифом из того, что ты успел узнать.
- **Compact** — сжать сессию в сводку и продолжить поверх неё.
- **Субагенты** — делегировать следующий кусок работы агенту с чистым контекстом, забрать только результат.

Инстинктивный выбор — Continue, но остальные четыре варианта существуют именно для управления контекстом.

Каждый вариант переносит вперёд разный объём существующего контекста:

| Новая сессия | Compact | Субагент | Rewind | Continue |
| --- | --- | --- | --- | --- |
| только твой бриф | сводка с потерями | всё + результат | префикс цел, хвост обрублен | всё остаётся |
| *ничего* |  |  |  | *всё* |

### Когда начинать новую сессию

С 1M-контекстом задачи можно вести дольше — например, собрать full-stack-приложение в одной сессии. Но это не значит, что нужно сидеть в ней до упора.

**Общее правило: новая задача — новая сессия.**

Серая зона — связанные задачи, в которых часть контекста ещё нужна, но не весь. Например, написать документацию к фиче, которую только что собрал. В новой сессии Claude переоткроет файлы — это медленнее и дороже. Документация не требует особой сообразительности, и контекст разумно сохранить ради эффективности.

### Rewind вместо коррекции

Если бы Thariq выбирал одну привычку, по которой видно хорошее управление контекстом, — это **rewind**.

В Claude Code двойной Esc (или `/rewind`) откатывает к любому предыдущему сообщению и даёт переписать промпт оттуда. Всё, что было после этой точки, выпадает из контекста.

**Коррекция** (после неудачной попытки A сказать «нет, попробуй B») оставляет в контексте всё:

> контекст = чтения + 2 неудачные попытки + 2 коррекции + фикс

**Rewind** (откатиться до момента перед неудачной попыткой и заново прописать промпт с учётом того, что узнал) — чище:

> контекст = чтения + один информированный промпт + фикс

Rewind обычно лучше. Пример: Claude прочитал пять файлов, попробовал подход, не сработало. Инстинкт — «не получилось, попробуй X». Лучше — откатиться к точке после чтений и переписать промпт со знанием дела: «Не используй подход A, модуль foo не отдаёт это поле — иди сразу к B».

Можно использовать **«summarize from here»**, чтобы Claude свернул выученное в handoff-сообщение — что-то вроде записки прошлой версии Claude от будущей, которая попробовала и узнала, что так не работает.

### Compact против /clear

Когда сессия раздулась, есть два способа разгрузить: `/compact` или `/clear` (и стартовать заново). Внешне похоже, ведут себя по-разному.

**Compact** просит модель суммировать разговор и заменяет историю этой сводкой. Сжатие с потерями: ты доверяешь Claude решать, что было важно, но сам ничего не пишешь. Claude может включить ключевые находки и файлы плотнее, чем сделал бы ты. И можно подсказать, на чём держать фокус: `/compact focus on the auth refactor, drop the test debugging`.

- **В середине задачи**, чтобы не терять разгон — детали могут быть размытыми.
- Дёшево, едем дальше.

**Свежая сессия + бриф** (`/clear`) — *ты* выписываешь, что важно («рефакторим auth-middleware, ограничение — X, важные файлы — A и B, подход Y исключили»), и стартуешь чисто. Больше работы, зато итоговый контекст — ровно тот, который *ты* признал релевантным.

- **Высокие ставки** на следующем шаге — одна находка в 100K разведки.
- Больше работы, но точнее.

### Что делает compact плохим?

Если ты часто гоняешь длинные сессии, наверняка замечал моменты, когда compact выходит особенно неудачным. Плохой compact случается, когда модель не может предсказать, куда дальше пойдёт работа.

Например: автокомпакция срабатывает после долгого дебага и сжимает разбор. Следующее твоё сообщение — «теперь почини то другое предупреждение, которое мы видели в `bar.ts`». Но поскольку сессия фокусировалась на дебаге, это другое предупреждение могло выпасть из сводки.

Усугубляется тем, что из-за context rot модель в момент компакции находится в самой «тупой» своей точке. С миллионом токенов у тебя теперь больше времени вызвать `/compact` проактивно — с описанием того, что хочешь делать дальше.

### Субагенты и свежие контекст-окна

Субагенты — тоже инструмент управления контекстом, полезный, когда заранее знаешь: кусок работы породит много промежуточного вывода, который потом не понадобится.

Когда Claude поднимает субагента через Agent-инструмент, тот получает своё свежее контекст-окно. Делает сколько надо работы, синтезирует результат — и в родительский контекст возвращается только финальный отчёт.

Ментальный тест: **понадобится ли мне этот вывод инструмента ещё раз — или хватит заключения?**

Промежуточный шум исследования выбрасывается вместе с субагентом: 20 чтений файлов, 12 grep-ов, 3 тупика — наружу вернётся только финальный отчёт.

Claude Code сам зовёт субагентов, когда это уместно, но иногда стоит сказать явно:

- «Подними субагента, чтобы проверить результат этой работы по такому-то спеку».
- «Подними субагента, чтобы пройти эту чужую кодовую базу и описать, как там реализован auth-flow; потом реализуй у нас так же».
- «Подними субагента, чтобы написать доку по фиче на основе моих git-изменений».

### Резюме

Когда Claude закончил ход и ты собираешься писать следующее сообщение — у тебя точка решения. Со временем Claude будет рулить этим сам, но пока — это один из способов направить его вывод.

| Ситуация | Что выбрать | Почему |
| --- | --- | --- |
| Та же задача, контекст всё ещё работает на неё | **Continue** | Всё, что в окне, по-прежнему несущее — нет смысла перестраивать |
| Claude ушёл не туда | **Rewind** (двойной Esc) | Сохраняем полезные чтения, выбрасываем неудачу, переписываем промпт со знанием |
| В середине задачи, но сессия раздулась устаревшим дебагом/разведкой | **/compact \<подсказка>** | Дёшево; Claude сам решает что оставить, направь подсказкой если надо |
| Начинаешь по-настоящему новую задачу | **/clear** | Нулевой rot; ты сам контролируешь, что переносится |
| Следующий шаг даст много вывода, от которого нужно только заключение | **Субагент** | Промежуточный шум остаётся в контексте субагента; наверх приходит только результат |

## Boris Cherny — 15 скрытых и недоиспользованных фич · 30 марта 2026

**Источник:** [тред в X от 30 марта 2026](https://x.com/bcherny/status/2038454336355999749) — любимые скрытые и недоиспользованные возможности Claude Code, которыми Boris пользуется чаще всего.

### 1. У Claude Code есть мобильное приложение

Знал, что у Claude Code есть мобильное приложение? Boris пишет много кода прямо из iOS-приложения — удобно делать правки, не открывая ноутбук.

- Качаешь приложение Claude для iOS/Android.
- На левой панели — вкладка **Code**.
- Прямо с телефона можно ревьюить изменения, апрувить PR-ы и писать код.

### 2. Перенос сессий между mobile/web/desktop и терминалом

`claude --teleport` или `/teleport` — продолжить облачную сессию на своей машине. `/remote-control` — управлять локально запущенной сессией с телефона/веба.

- **Teleport** — стягивает облачную сессию вниз, в локальный терминал.
- **Remote Control** — позволяет управлять локальной сессией с любого устройства.
- У Boris в `/config` включено **«Enable Remote Control for all sessions»**.

### 3. `/loop` и `/schedule` — две самые мощные фичи

С их помощью Claude запускается автоматически с заданным интервалом, до недели подряд. У Boris в фоне крутится куча циклов:

- `/loop 5m /babysit` — авто-обрабатывает code review, делает rebase, доводит PR-ы до прода.
- `/loop 30m /slack-feedback` — открывает PR-ы под фидбек из Slack каждые 30 минут.
- `/loop /post-merge-sweeper` — открывает PR-ы на code-review-замечания, которые он пропустил.
- `/loop 1h /pr-pruner` — закрывает устаревшие и ставшие ненужными PR-ы.
- …и много чего ещё.

Стоит поэкспериментировать и превращать рабочие процессы в связку «скилл + loop».

### 4. Хуки — детерминированная логика в жизненном цикле агента

Хуки прикручивают логику к жизненному циклу агента. Примеры:

- **Динамически подгружать контекст** при каждом старте Claude (`SessionStart`).
- **Логировать каждую bash-команду**, которую запускает модель (`PreToolUse`).
- **Роутить permission-промпты в WhatsApp**, чтобы апрувить/отказывать прямо оттуда (`PermissionRequest`).
- **Пинать Claude**, чтобы продолжал, как только остановился (`Stop`).

### 5. Cowork Dispatch

Boris пользуется Dispatch каждый день: разгребает Slack и почту, управляет файлами, делает дела на ноутбуке, даже если не сидит за компьютером. Когда не кодит — диспатчит.

- Dispatch — это **защищённый remote-control** для приложения Claude Desktop.
- Может использовать твои MCP, браузер и компьютер — с твоего разрешения.
- Думай о нём как о способе делегировать Claude не-кодерские задачи откуда угодно.

### 6. Chrome-расширение для фронтенд-работы

Самый важный совет по использованию Claude Code: **дай Claude способ верифицировать результат.** Если он у него есть, Claude будет итерировать до тех пор, пока результат не станет хорошим.

- Представь, что просишь человека собрать сайт, но запрещаешь открывать браузер — результат вряд ли будет приличным.
- Дай Claude браузер — он будет писать и переписывать код, пока всё не будет выглядеть как надо.
- Boris пользуется Chrome-расширением каждый раз, когда работает с веб-кодом, — оно работает стабильнее аналогов через MCP.

### 7. Claude Desktop сам запускает и тестирует веб-серверы

В ту же сторону: в Claude Desktop встроена возможность **автоматически запустить твой веб-сервер и даже потестить его во встроенном браузере.**

- В CLI или VS Code можно собрать что-то похожее через Chrome-расширение.
- Либо просто использовать Desktop ради интегрированного опыта.

### 8. Форк сессии

Часто спрашивают, как форкнуть существующую сессию. Два способа:

1. Запустить `/branch` прямо в сессии.
2. Из CLI: `claude --resume <session-id> --fork-session`.

`/branch` создаёт ветвящийся разговор — ты оказываешься в ветке. Чтобы вернуться к оригиналу, используй `claude -r <original-session-id>`.

### 9. `/btw` — побочные вопросы

Boris использует это постоянно, чтобы быстро получить ответ на побочный вопрос, пока агент работает. `/btw` даёт спросить что-то на стороне, не прерывая текущую задачу.

Пример:

```
/btw how do I spell dachshund?
> dachshund — German for "badger dog" (dachs + badger, hund + dog).
↑/↓ to scroll · Space, Enter, or Escape to dismiss
```

### 10. Git worktrees

В Claude Code глубокая поддержка git worktrees. Worktrees незаменимы, когда нужно вести много параллельной работы в одном репозитории. У Boris **десятки Claude крутятся одновременно** — именно так.

- `claude -w` — стартует новую сессию в worktree.
- Либо галочка **«worktree»** в приложении Claude Desktop.
- Для пользователей не-Git VCS — хук `WorktreeCreate` позволяет накрутить свою логику создания worktree.

### 11. `/batch` — массовые changeset-ы веером

`/batch` берёт интервью у тебя, потом раскладывает работу веером на нужное количество **worktree-агентов** — десятки, сотни, даже тысячи.

- Используется для больших миграций кода и другой параллелизуемой работы.
- Каждый worktree-агент работает независимо, на своей копии кодовой базы.

### 12. `--bare` — до 10× ускоряет старт SDK

По умолчанию при запуске `claude -p` (или TypeScript/Python SDK) Claude ищет локальные `CLAUDE.md`, settings и MCP. Но в неинтерактивном режиме почти всегда хочется явно указать, что загружать, через `--system-prompt`, `--mcp-config`, `--settings` и т.д.

- Это был просчёт дизайна, когда SDK только собирали.
- В будущей версии дефолт перевернут на `--bare`.
- Пока — опт-ин флагом, выигрыш до **10× ускорения старта**.

```
claude -p "summarize this codebase" \
    --output-format=stream-json \
    --verbose \
    --bare
```

### 13. `--add-dir` — доступ к другим папкам

Когда работаешь сразу в нескольких репозиториях, Boris обычно стартует Claude в одном и через `--add-dir` (или `/add-dir`) даёт видеть второй.

- Это не только сообщает Claude о репо, но и **выдаёт разрешения** работать в нём.
- Либо положи `"additionalDirectories"` в командный `settings.json` — чтобы дополнительные папки подгружались автоматически при старте.

### 14. `--agent` — кастомный system prompt и тулы

Кастомные агенты — мощный примитив, который часто упускают. Чтобы воспользоваться, опиши агента в `.claude/agents/` и запусти:

```
claude --agent=<имя-агента>
```

- У агента могут быть ограниченные тулы, кастомное описание, конкретная модель.
- Подходит для read-only-агентов, специализированных ревью-агентов и доменных инструментов.

### 15. `/voice` — голосовой ввод

Забавный факт: Boris бо́льшую часть кода надиктовывает Claude голосом, а не пишет руками.

- В CLI: `/voice`, дальше зажимаешь пробел и говоришь.
- В Desktop: кнопка голосового ввода.
- Либо включить диктовку в настройках iOS.

| --- | --- | --- |

- Маленькие PR-ы снижают риск конфликтов мержа, проще ревьюятся, идеально сочетаются со squash-мержем для чистых откатов.

## Thariq — Как мы используем скиллы внутри Anthropic · 17 марта 2026

**Источник:** [гайд Thariq от 17 марта 2026](https://x.com/trq212/status/2033949937936085378) — сотни активно используемых скиллов внутри Anthropic, выученные уроки.

### Контекст

Скиллы стали одной из самых популярных точек расширения Claude Code. Они гибкие, легко собираются и распространяются. Но та же гибкость затрудняет понимание, что работает лучше всего. Thariq делится уроками из практики Anthropic.

### Что такое скиллы

Распространённое заблуждение: «скилл — это просто markdown-файл». На самом деле самое интересное — что скиллы это **папки**, которые могут содержать скрипты, ассеты, данные и т.д. — то, что агент может находить, изучать и использовать. У скиллов также есть множество опций конфигурации, включая регистрацию динамических хуков.

### Типы скиллов

После каталогизации всех скиллов команда заметила, что они кластеризуются в **9 повторяющихся категорий**. Лучшие скиллы чисто попадают в одну категорию; более путаные размазаны на несколько.

#### 1. Библиотека и API Reference

Скиллы, объясняющие, как правильно использовать библиотеку, CLI или SDK. Это могут быть внутренние библиотеки или популярные библиотеки, с которыми у Claude Code иногда бывают проблемы. Часто включают папку с эталонными сниппетами и список «грабель», которых стоит избегать при написании скрипта.

**Примеры:** `billing-lib`, `internal-platform-cli`, `frontend-design`.

#### 2. Product Verification

Скиллы, описывающие, как тестировать или проверять, что код работает. Часто работают в паре с внешним инструментом — Playwright, tmux и т.д. Скиллы верификации крайне полезны для гарантии корректности вывода Claude. Стоит потратить неделю инженерного времени, чтобы довести их до отличного состояния.

**Примеры:** `signup-flow-driver`, `checkout-verifier`, `tmux-cli-driver`.

#### 3. Получение и анализ данных

Скиллы, подключающиеся к твоим стэкам данных и мониторинга. Включают библиотеки для получения данных с креденшелами, ID конкретных дашбордов и т.п., а также инструкции по типичным workflow и способам получить данные.

**Примеры:** `funnel-query`, `cohort-compare`, `grafana`.

#### 4. Бизнес-процессы и автоматизация команды

Скиллы, упаковывающие повторяющиеся workflow в одну команду. Обычно довольно простые инструкции, но могут иметь сложные зависимости от других скиллов или MCP. Сохранение прошлых результатов в лог-файлах помогает модели оставаться консистентной и опираться на предыдущие запуски.

**Примеры:** `standup-post`, `create-<ticket-system>-ticket`, `weekly-recap`.

#### 5. Code Scaffolding и шаблоны

Скиллы, генерирующие boilerplate фреймворка под конкретную функцию в кодовой базе. Удобно комбинировать со скриптами, которые компонуются. Особенно полезны, когда у скэффолдинга есть требования на естественном языке, которые чистым кодом не покрыть.

**Примеры:** `new-<framework>-workflow`, `new-migration`, `create-app`.

#### 6. Code Quality и Review

Скиллы, обеспечивающие качество кода внутри организации и помогающие ревьюить код. Могут включать детерминированные скрипты или тулы для максимальной устойчивости. Их стоит запускать автоматически — как часть хуков или внутри GitHub Action.

**Примеры:** `adversarial-review`, `code-style`, `testing-practices`.

#### 7. CI/CD и деплой

Скиллы, помогающие получать, пушить и деплоить код в твоей кодовой базе. Могут ссылаться на другие скиллы для сбора данных.

**Примеры:** `babysit-pr`, `deploy-<service>`, `cherry-pick-prod`.

#### 8. Runbooks

Скиллы, которые берут симптом (Slack-тред, алёрт, сигнатуру ошибки), проходят мульти-тул-расследование и выдают структурированный отчёт.

**Примеры:** `<service>-debugging`, `oncall-runner`, `log-correlator`.

#### 9. Инфраструктурные операции

Скиллы, выполняющие рутинное обслуживание и операционные процедуры — часть из них включает разрушительные действия, для которых нужны ограничители. Помогают инженерам следовать лучшим практикам в критичных операциях.

**Примеры:** `<resource>-orphans`, `dependency-management`, `cost-investigation`.

### Советы по созданию скиллов

Девять лучших практик плюс гайд по распространению и измерению.

#### Совет 1. Не пиши очевидное

Claude Code знает много о твоей кодовой базе, а Claude знает много о программировании в целом, включая множество дефолтных мнений. Если публикуешь скилл, основная ценность которого — знание, фокусируйся на информации, **выталкивающей Claude из его обычного режима мышления**. Скилл `frontend-design` — хороший пример: его делали итерациями с пользователями, прокачивая дизайн-вкус Claude, избегая классических паттернов вроде шрифта Inter и фиолетовых градиентов.

#### Совет 2. Заводи секцию Gotchas

В любом скилле самый высокосигнальный контент — секция **Gotchas** («грабли»). Её надо отстраивать из типичных мест провала Claude при использовании твоего скилла. По-хорошему ты будешь обновлять скилл со временем, добавляя туда новые случаи.

#### Совет 3. Используй файловую систему и progressive disclosure

Скилл — это папка, а не просто markdown-файл. Думай обо всей файловой системе как о форме context engineering и progressive disclosure. Скажи Claude, какие файлы есть в скилле, — и он прочитает их в нужный момент. Самая простая форма — указывать на другие markdown-файлы: например, вынести детальные сигнатуры функций и примеры использования в `references/api.md`. Можно иметь папки `references/`, `scripts/`, `examples/` и т.д.

#### Совет 4. Не загоняй Claude в рельсы

Claude в целом старается следовать твоим инструкциям, а поскольку скиллы переиспользуются — будь осторожен с излишней конкретикой. Дай Claude информацию, которая ему нужна, но оставь гибкость подстраиваться под ситуацию. Вместо предписывающих пошаговых инструкций — давай цель и ограничения.

#### Совет 5. Продумай настройку

Некоторым скиллам нужен сетап с контекстом от пользователя. Хороший паттерн — хранить эту настройку в файле `config.json` в директории скилла. Если конфиг не настроен — агент попросит пользователя ввести нужную информацию. Можно инструктировать Claude использовать инструмент AskUserQuestion для структурированных вопросов с вариантами ответа.

#### Совет 6. Поле description — для модели

Когда Claude Code стартует сессию, он строит список всех доступных скиллов вместе с их описаниями. По этому списку Claude решает, «есть ли скилл под этот запрос?». Это значит, что поле `description` — не саммари, а **описание триггера**: когда этот скилл должен сработать. Пиши его для модели.

#### Совет 7. Память и хранение данных

Скиллы могут включать форму памяти, храня данные внутри себя. Можно хранить что угодно — от append-only лог-файла или JSON-файла до SQLite-базы. Данные в директории скилла могут быть удалены при апгрейде скилла, поэтому используй `${CLAUDE_PLUGIN_DATA}` как стабильную папку на плагин для хранения данных.

#### Совет 8. Храни скрипты и генерируй код

Один из самых мощных инструментов, которые можно дать Claude, — это код. Дав Claude скрипты и библиотеки, ты освобождаешь его ходы на композицию: что делать дальше, а не «как воспроизвести boilerplate». Дальше Claude может на лету генерировать скрипты для более продвинутого анализа.

#### Совет 9. Хуки по требованию

Скиллы могут включать хуки, которые активируются только при вызове скилла и работают до конца сессии. Используй для более «opinionated» хуков, которые не нужно запускать всегда, но иногда они крайне полезны.

**Примеры:**

- `/careful` — блокирует `rm -rf`, `DROP TABLE`, force-push, `kubectl delete` через PreToolUse-матчер на Bash.
- `/freeze` — блокирует любой Edit/Write вне конкретной директории.

### Распространение скиллов

Два способа делиться скиллами с командой:

- **Чекин в репо** (под `.claude/skills`) — лучше для маленьких команд, работающих в нескольких репозиториях.
- **Сделать плагин** и иметь Claude Code Plugin Marketplace, куда пользователи могут заливать и откуда устанавливать плагины.

Каждый счекиненный скилл немного добавляет в контекст модели. По мере масштабирования внутренний marketplace плагинов позволяет распространять скиллы и давать команде самой решать, что устанавливать.

### Управление marketplace-ом

Нет централизованной команды, которая решает, какие скиллы попадают в marketplace. Подход — органически находить самые полезные скиллы. Заливай в sandbox-папку на GitHub, рассказывай в Slack и других каналах. Когда у скилла появилась тяга (а решает это владелец скилла) — открывай PR, чтобы перенести его в marketplace. Курирование до релиза важно, чтобы не плодить дубли.

### Композиция скиллов

Скиллы могут зависеть друг от друга. Например, скилл upload-файла загружает файл, а скилл генерации CSV — делает CSV и загружает его. Управление такими зависимостями в marketplace и скиллах пока не встроено, но можно просто ссылаться на другие скиллы по имени — модель вызовет их, если они установлены.

### Измерение скиллов

Чтобы понимать, как скилл работает, заведи PreToolUse-хук и логируй использование скиллов внутри компании. Так найдёшь популярные скиллы и те, что недосрабатывают относительно ожиданий.

### Заключение

Скиллы — мощные и гибкие инструменты для агентов, но пока всё в начале, и мы всё ещё разбираемся, как использовать их по максимуму. Думай об этом гайде скорее как о наборе полезных приёмов, которые мы видели в работе, а не как об окончательной инструкции. Лучший способ разобраться — начать, экспериментировать и смотреть, что работает у тебя. Большинство наших скиллов начинались с нескольких строк и одной «грабли», и стали лучше по мере того, как люди добавляли в них новые edge-кейсы.

## Boris Cherny — 12 способов кастомизировать Claude Code · 12 февраля 2026

**Источник:** [тред в X от 12 февраля 2026](https://x.com/bcherny/status/2021699851499798911) — кастомизация (хуки, плагины, LSP, MCP, скиллы, effort, агенты, status line, output styles) это одна из главных причин, за что инженеры любят Claude Code.

### 1. Настрой терминал

Подготовь терминал под комфортную работу с Claude Code:

- **Тема:** `/config` — переключение light/dark.
- **Уведомления:** включи нотификации для iTerm2 или повесь свой нотификационный хук.
- **Newlines:** если работаешь в IDE-терминале, Apple Terminal, Warp или Alacritty — `/terminal-setup` включит Shift+Enter для переноса строки (чтобы не печатать `\`).
- **Vim-режим:** `/vim`.

### 2. Настрой уровень effort

`/model` — выбрать предпочитаемый уровень effort:

- **Low** — меньше токенов, быстрее ответ.
- **Medium** — сбалансированно.
- **High** — больше токенов, больше интеллекта.

Предпочтение Boris: High для всего.

### 3. Ставь плагины, MCP и скиллы

Плагины позволяют ставить LSP-серверы (под каждый крупный язык), MCP, скиллы, агентов и кастомные хуки.

Ставь из официального marketplace-а Anthropic, либо подними свой marketplace для компании. Зачекинь `settings.json` в кодовую базу — это автоматически подключит marketplace всей команде.

`/plugin` — точка входа.

### 4. Создавай кастомных агентов

Бросай `.md`-файлы в `.claude/agents` — это и есть кастомный агент. У каждого может быть своё имя, цвет, набор тулов, пред-разрешённые и пред-запрещённые тулы, permission-режим, модель.

Можно задать дефолтного агента для основного разговора через поле `"agent"` в `settings.json` или флаг `--agent`.

`/agents` — точка входа.

### 5. Пред-апрувь типичные permissions

Permission-система Claude Code сочетает детекцию prompt-injection, статический анализ, sandboxing и человеческий контроль.

Из коробки апрувлен маленький набор безопасных команд. Чтобы добавить ещё — `/permissions`, дальше allow/block списки. Зачекинь в командный `settings.json`.

Поддерживается полная wildcard-нотация — например, `Bash(bun run *)` или `Edit(/docs/**)`.

### 6. Включай sandboxing

Опт-ин в open-source sandbox runtime Claude Code: повышает безопасность и снижает число permission-промптов.

`/sandbox` — включить. Песочница работает локально и поддерживает изоляцию по файловой системе и по сети.

### 7. Добавь status line

Кастомные status line выводятся прямо под композером — показывают модель, директорию, остаток контекста, стоимость и всё, что тебе важно держать в поле зрения.

У каждого в команде может быть свой статуслайн. `/statusline` — попросить Claude сгенерировать его на основе твоего `.bashrc` / `.zshrc`.

### 8. Настраивай keybindings

В Claude Code кастомизируется каждое сочетание клавиш. `/keybindings` — переназначить. Настройки применяются на лету, эффект виден сразу.

### 9. Заводи хуки

Хуки дают детерминированную «врезку» в жизненный цикл Claude:

- Авто-роутить permission-запросы в Slack или к Opus.
- Подталкивать Claude продолжать, когда он завершил ход (можно даже запустить агента или промпт, который решит, надо ли продолжать).
- Пре- или пост-процессить tool-вызовы — например, добавить своё логирование.

Самый простой способ начать — попросить Claude добавить хук.

### 10. Кастомизируй spinner verbs

Кастомизируй глаголы у спиннера — добавь или замени дефолтные на свои. Зачекинь `settings.json` под версионный контроль, чтобы поделиться с командой.

### 11. Output styles

`/config` → выбери output style, чтобы Claude отвечал в другом тоне или формате.

- **Explanatory** — рекомендуется, когда осваиваешь новую кодовую базу: Claude объясняет фреймворки и паттерны прямо по ходу работы.
- **Learning** — Claude будет коучить тебя через изменения в коде.
- **Custom** — свой output-style под нужный голос.

### 12. Кастомизируй всё подряд

Claude Code хорошо работает «из коробки», но когда настраиваешь — обязательно чекинь `settings.json` в git, чтобы пользу получила вся команда. Конфигурация поддерживается на нескольких уровнях:

- На кодовую базу.
- На вложенную папку.
- Только для себя.
- Через enterprise-политики.

У Claude Code 37 настроек и 84 переменных окружения (используй поле `"env"` в `settings.json` вместо wrapper-скриптов), так что почти любое поведение, которое тебе нужно, — настраиваемо.

## Boris Cherny — 10 советов от команды Claude Code · 1 февраля 2026

**Источник:** [тред в X от 1 февраля 2026](https://x.com/bcherny/status/2017742741636321619) — сборка советов от самой команды Claude Code. Каждый внутри Anthropic использует Claude по-своему — нет одного правильного сетапа, нужно пробовать.

### 1. Делай больше параллельно

Запускай **3–5 git worktrees** одновременно, в каждом — своя сессия Claude. Это самый большой апгрейд продуктивности и совет №1 от команды. Сам Boris использует несколько git-чекаутов, но большинство команды Claude Code предпочитает worktrees — именно поэтому `@amorisscode` сделал нативную поддержку worktrees в Claude Desktop.

Кто-то именует worktrees и заводит shell-алиасы (`2a`, `2b`, `2c`), чтобы переключаться одним нажатием. У других есть отдельный worktree «analysis» — только для логов и BigQuery.

См. [Worktrees Docs](https://code.claude.com/docs/en/worktrees).

### 2. Любую сложную задачу начинай в plan mode

Вкладывайся в план — тогда Claude сможет реализовать всё за один заход.

Кто-то один Claude пишет план, второй ревьюит его как staff-инженер.

Кто-то говорит: как только что-то идёт не туда — сразу обратно в plan mode и переплановать. Не продавливать. Plan mode они включают и под этап верификации, не только под сборку.

### 3. Вкладывайся в `CLAUDE.md`

После каждой коррекции заканчивай словами: «Update your CLAUDE.md so you don't make that mistake again». Claude жутковато хорош в написании правил для самого себя.

Безжалостно редактируй `CLAUDE.md` со временем. Итерируй, пока доля ошибок Claude измеримо не упадёт.

Один инженер просит Claude вести папку заметок на каждую задачу/проект, обновляемую после каждого PR. Потом этот путь прописан в `CLAUDE.md`.

### 4. Пиши свои скиллы и чекинь их в git

Переиспользуй между проектами. Советы от команды:

- Если что-то делаешь больше раза в день — превращай в скилл или slash-команду.
- Собери `/techdebt` и запускай в конце каждой сессии, чтобы находить и убивать дубли.
- Заведи slash-команду, которая собирает 7 дней Slack, GDrive, Asana и GitHub в один контекстный дамп.
- Собирай аналитика-инженер-агентов: пишут dbt-модели, ревьюят код, тестируют изменения в dev.

См. [Skills Docs](https://code.claude.com/docs/en/skills).

### 5. Claude чинит большинство багов сам

Как это делает команда:

Включи Slack MCP, кидай в Claude Slack-тред с багом, говори «fix». Никакого переключения контекста.

Или просто скажи: «Go fix the failing CI tests». Не микроменеджи как.

Направь Claude на docker-логи разобраться в распределённой системе — удивительно хорошо справляется.

### 6. Прокачивай промптинг

a. **Прокатывай Claude через жёсткое.** «Grill me on these changes and don't make a PR until I pass your test» — пусть Claude станет твоим ревьюером. Или: «Prove to me this works» — пусть Claude диффает поведение между main и фича-веткой.

b. **После посредственного фикса** скажи: «Knowing everything you know now, scrap this and implement the elegant solution».

c. **Пиши детальные спеки**, убирай двусмысленности до того, как отдашь работу. Чем конкретнее, тем лучше результат.

### 7. Терминал и окружение

Команда обожает Ghostty: синхронизированный рендеринг, 24-bit цвет, нормальный Unicode.

Чтобы было легче «жонглировать» несколькими Claude — настрой `/statusline`, чтобы статусная строка всегда показывала использование контекста и текущую git-ветку. Многие к тому же цветокодируют и именуют вкладки терминала, кто-то — через tmux: одна вкладка на задачу/worktree.

Используй voice dictation. Говоришь в 3× быстрее, чем печатаешь, и промпты выходят гораздо более детальными. (На macOS — `fn` дважды.)

См. [Terminal Setup Docs](https://code.claude.com/docs/en/terminal).

### 8. Используй субагентов

a. Добавляй «use subagents» к любому запросу, где хочешь, чтобы Claude бросил на проблему больше compute.

b. Сгружай отдельные задачи на субагентов — контекст основного агента остаётся чистым и сфокусированным.

c. Роуть permission-запросы на Opus 4.5 через хук — пусть он сканирует на атаки и авто-апрувит безопасные. См. [Hooks Docs](https://code.claude.com/docs/en/hooks).

### 9. Используй Claude для данных и аналитики

Попроси Claude Code воспользоваться `bq` CLI, чтобы вытянуть и посчитать метрики на лету. У команды есть BigQuery-скилл, зачекиненный в кодовую базу — все гоняют аналитические запросы прямо из Claude Code. Сам Boris не написал ни строчки SQL уже больше 6 месяцев.

Работает с любой БД, у которой есть CLI, MCP или API.

### 10. Учёба с Claude

Несколько советов от команды, как использовать Claude Code для обучения:

a. Включи output style `Explanatory` или `Learning` в `/config` — Claude будет объяснять «почему» за своими изменениями.

b. Попроси Claude сгенерировать визуальную HTML-презентацию, объясняющую незнакомый код. Удивительно хорошо получается.

c. Попроси Claude рисовать ASCII-диаграммы новых протоколов и кодовых баз — помогает понять.

d. Собери скилл интервального повторения: ты объясняешь своё понимание, Claude задаёт уточняющие вопросы, чтобы закрыть пробелы, сохраняет результат.

## Boris Cherny — 13 советов о моём сетапе · 3 января 2026

**Источник:** [тред в X от 3 января 2026](https://x.com/bcherny/status/2007179832300581177) — личный сетап Boris, «удивительно ванильный»: Claude Code хорошо работает из коробки, поэтому он почти ничего не кастомизирует. Правильного способа использовать его нет — команда специально строит инструмент так, чтобы каждый собирал его под себя.

### 1. Запускай 5 Claude параллельно

Запускай 5 Claude параллельно в терминале. Пронумеруй вкладки 1–5, включи системные нотификации — чтобы знать, какому Claude нужен ввод.

См. [Terminal Setup Docs](https://code.claude.com/docs/en/terminal).

### 2. claude.ai/code — ещё больше параллелизма

Запускай ещё 5–10 Claude на `claude.ai/code` параллельно с локальными. Передавай локальные сессии в веб через `claude.ai/code`, вручную поднимай сессии в Chrome, телепортируй туда-обратно.

### 3. Opus с thinking — для всего

Используй **Opus 4.5 с thinking** для всего. Это лучшая модель для кода, какую Boris видел, — да, она больше и медленнее Sonnet, но её приходится меньше «рулить», она лучше с тулами, и в итоге почти всегда выходит быстрее меньшей модели.

### 4. Один `CLAUDE.md` на репо, на всю команду

Сделай **один общий `CLAUDE.md` на репо**. Зачекинь в git и пусть вся команда контрибьютит в него несколько раз в неделю. Как только Claude делает что-то неправильно — добавляй это в `CLAUDE.md`, чтобы в следующий раз он так не делал.

### 5. Тегай `@claude` на PR-ах, чтобы апдейтить `CLAUDE.md`

На code review тегай `@claude` на PR-ах коллег — пусть добавит правило в `CLAUDE.md` прямо в рамках PR. Для этого — [Claude Code GitHub action](https://github.com/apps/claude). У Boris это его версия Compounding Engineering.

### 6. Большинство сессий — в plan mode

Стартуй большинство сессий в plan mode (`Shift+Tab` дважды). Если цель — открыть PR, поработай в plan mode туда-сюда, пока план не понравится. Дальше переключаешься в auto-accept edits — Claude обычно делает всё с первого раза. Хороший план — это правда важно.

### 7. Slash-команды для inner-loop-workflow

Используй slash-команды для каждого inner-loop workflow, который повторяешь несколько раз в день. Избавляет от повторяющегося промптинга, и Claude тоже может ими пользоваться. Команды чекинятся в git и живут в `.claude/commands/`.

Пример: `/commit-push-pr` — закоммитить, запушить, открыть PR.

### 8. Субагенты для автоматизации частых workflow

Заведи несколько постоянных субагентов: `code-simplifier` упрощает код после того, как Claude закончил; `verify-app` имеет детальные инструкции по end-to-end-тестированию Claude Code; и так далее. Думай о субагентах как об автоматизации самых частых workflow — аналогично slash-командам.

Субагенты живут в `.claude/agents/`.

### 9. `PostToolUse` хук для авто-форматирования

Используй хук `PostToolUse` для форматирования кода Claude. Claude обычно выдаёт уже неплохо отформатированный код — хук закрывает последние 10%, чтобы CI потом не падал на форматировании.

```json
"PostToolUse": [
  {
    "matcher": "Write|Edit",
    "hooks": [
      {
        "type": "command",
        "command": "bun run format || true"
      }
    ]
  }
]
```

### 10. Пред-разрешай permissions вместо `--dangerously-skip-permissions`

Не используй `--dangerously-skip-permissions`. Вместо этого через `/permissions` пред-разрешай типичные bash-команды, безопасные в твоём окружении, — это снимет ненужные permission-промпты. Большинство этих правил лежит в `.claude/settings.json` и шарится с командой.

### 11. Дай Claude все твои тулы через MCP

Claude Code использует все твои инструменты. Часто ищет и постит в Slack (через MCP-сервер), гоняет BigQuery-запросы для аналитики (через `bq` CLI), тащит логи ошибок из Sentry и т.д. Конфигурация Slack MCP чекинится в `.mcp.json` и шарится команде.

### 12. Верифицируй долгие задачи через фоновых агентов

Для очень долгих задач: (a) попроси Claude по завершении проверить работу через фонового агента, либо (b) повесь хук `Stop` на агента, чтобы делать это детерминированно, либо (c) используй плагин `ralph-wiggum` (придумал [@GeoffreyHuntley](https://github.com/ghuntley/how-to-ralph-wiggum)).

### 13. Дай Claude способ верифицировать свою работу

Вероятно, самое важное, что нужно сделать, чтобы Claude Code выдавал отличный результат — **дай ему способ проверить свою работу**. Если такой обратной связи у Claude нет — её появление улучшит итоговый результат в 2–3 раза.

Claude тестирует каждое изменение, которое Boris вливает.
