# Claude Code устроен трёхслойно: совет, условное, гарантия

> Черновик статьи для Habr. ~17K знаков. Все цифры и цитаты — из research-заметок автора, требуют финальной проверки перед публикацией (arXiv-ID, install-counts, формулировки официальной доки).

---

Полгода назад я начал собирать публичный handbook по Claude Code на русском. Чтобы он был не очередной свалкой ссылок, я ставил всё, на что наткнулся. За первый месяц у меня в `~/.claude/` оказалось 116 скиллов. Через тридцать дней я реально использовал 35. Остальные 81 ели токены контекста в каждой сессии и не делали ничего — модель про них просто не вспоминала.

Я было решил, что проблема в качестве скиллов. Сел писать [`skill-graveyard`](https://github.com/sfrangulov/skill-graveyard) — CLI-аудитор, который парсит логи сессий и сопоставляет с установленным. Когда отчёт был готов, я понял другое: проблема не в скиллах. Проблема в том, что я пытался решать задачи не на том слое архитектуры.

В этой статье я разберу, как на самом деле устроен Claude Code, и покажу, почему 80% типичных советов из чатов и Habr-комментариев («пропиши в CLAUDE.md, что нельзя пушить в main», «поставь побольше скиллов, модель сама подтянет нужный») не работают — не по криворукости пользователя, а по архитектуре.

## Три слоя

Claude Code — это не «LLM с инструментами». Это три разнородных слоя, каждый со своими гарантиями:

| Слой | Что это | Гарантия |
|---|---|---|
| **CLAUDE.md** | Markdown в корне репо | Подгружается в контекст. Модель **может** учесть. |
| **Skills** | YAML + промпт в `.claude/skills/` | Активируются по триггеру в описании. Модель **обычно** активирует — если описание правильное. |
| **Hooks** | Shell-команда на событие сессии | Запускается всегда. Exit code 2 = жёсткий блок. |

Слова «может», «обычно», «всегда» — это не риторика, это разные классы поведения. CLAUDE.md — это **совет**. Skills — **условное правило**. Hook — **гарантия**.

Подавляющее большинство ошибок при настройке Claude Code — это попытка решить задачу слоем, который не даёт нужной гарантии. Хочешь, чтобы агент **никогда** не делал X — пишешь в CLAUDE.md «НИКОГДА не делай X!» с восклицательным знаком. Модель прочитает. Может учесть. Может не учесть. Никакого `never` в природе нет.

Дальше — что делает каждый слой и где у него предел.

## Слой 1. CLAUDE.md — совет, не enforcement

Anthropic в [официальной доке](https://docs.claude.com/en/docs/claude-code/memory) формулирует прямо: *«CLAUDE.md provides context, not enforced configuration»*. Технически это файл, который Claude Code зачитывает в начале сессии и добавляет в системный промпт. С точки зрения модели это просто текст в контексте — такой же, как сообщение от пользователя, только сверху. У модели нет встроенного механизма «следовать CLAUDE.md строго». Она пытается. Иногда получается.

Эмпирика подтверждает, что «иногда получается» — не фигура речи.

**Первый ограничитель — лимит инструкций.** Frontier-модели надёжно следуют примерно 150-200 инструкциям одновременно (по оценке A. Opalic / HumanLayer). Из этих 150-200 системный промпт Claude Code уже забрал около 50: правила работы с инструментами, обработка ошибок, формат вывода. Остаётся ~100 на пользовательский CLAUDE.md плюс реальную задачу. Перевалил за 200 строк осмысленных правил — модель начинает молча игнорировать часть.

**Второй ограничитель — контекстные файлы могут вредить.** Исследование ETH Zurich (arXiv:2602.11988, фиксируйте этот ID при публикации — я цитирую по своим заметкам) измеряло влияние persistent-context файлов на task-success для разных coding-агентов. Для большинства агентов результат положительный. Для Claude Code конкретно — **−4% task success** в среднем. Контекстный файл, забитый «важными» правилами, отвлекает модель от собственно задачи.

Это контринтуитивно. Здравый смысл подсказывает «больше контекста → лучше решение». Эмпирика говорит другое: больше шума → хуже фокус.

**Антипаттерн, который я вижу в чужих CLAUDE.md чаще всего:**

```markdown
## ВАЖНО! ОБЯЗАТЕЛЬНО!

- НИКОГДА не используй `any` в TypeScript!
- ВСЕГДА пиши тесты ПЕРЕД кодом!
- ОБЯЗАТЕЛЬНО комментируй каждую публичную функцию!
- НЕ ИСПОЛЬЗУЙ console.log в production!
- ЗАПРЕЩЕНО коммитить без code-review!
```

Каждая такая строчка — попытка превратить совет в приказ через капитализацию. Модель прочтёт, кивнёт, всё равно сделает то, что ей кажется правильнее в момент действия. «ЗАПРЕЩЕНО коммитить без code-review» особенно показательно — это вообще не задача LLM, это задача git-hook.

**Что работает:**

```markdown
## TypeScript

Strict mode. `any` запрещён в новом коде — используй `unknown` + type narrowing.

## Testing

TDD: тест → код → рефактор. Раннер: `pnpm test`.

## Database

Read-only по умолчанию. Миграции через `pnpm migrate`, не вручную в SQL-клиенте.
```

Лаконично, нейтральным тоном, без капса. CLAUDE.md как **контекст** для модели, а не как **правила** для подчинённого.

Эмпирическое правило: если ты пишешь в CLAUDE.md «НИКОГДА X», прочитай ещё раз. Если последствия «модель сделала X» серьёзные (упал прод, утёк секрет, потерялись данные) — это не CLAUDE.md. Это hook.

## Слой 2. Skills — условное правило

Skill — это самостоятельный артефакт: папка `.claude/skills/<name>/` с файлом `SKILL.md` внутри. У файла YAML-фронтматтер с двумя главными полями: `name` и `description`. Тело — markdown с инструкциями, что и как делать.

Активация работает так. Перед каждой задачей модель видит список всех установленных скиллов с их `description`. Решает, какие из них релевантны текущему запросу пользователя. Подгружает выбранные в контекст. Дальше следует инструкциям из тела.

Это **умнее**, чем CLAUDE.md (контекст подгружается выборочно, токены экономятся), и **надёжнее**, чем «общий совет» (если активирован, инструкции свежие). Но это всё ещё не гарантия. Это эвристика.

И эта эвристика очень зависит от формулировки `description`.

**Цифры из независимого тестирования** (Seleznov, 650 испытаний на разных скиллах):

| Описание | Без hook'а | С PreToolUse-hook'ом |
|---|---:|---:|
| Passive («This skill helps with...») | ~50% | **37%** |
| Directive («Use when... ALWAYS invoke...») | ~80% | 100% |

Две вещи, которые ломают мейнстримовское представление:

**1.** Passive descriptions активируются хуже половины случаев. Большинство скиллов на skills.sh и в community-маркетплейсах написаны именно пассивно: «This skill provides X», «A tool for Y». Модель читает и думает: «возможно подходит, возможно нет». В половине сессий — нет.

**2.** Hook на passive description делает только хуже — 37% вместо 50%. Звучит как баг, но логика понятна: passive описание не даёт чётких триггеров, hook предоставляет дополнительный noise-сигнал, модель путается ещё сильнее. Hook'и работают только в паре с directive descriptions.

Это значит, что когда кто-то постит «поставил obra/superpowers — модель не использует скиллы, фиг знает почему» — проблема не в obra/superpowers (там descriptions хорошие). Проблема в трёх других скиллах из чьего-то community-набора, которые написаны пассивно и тащат вниз весь список.

**Второй контр-мейнстрим момент про skills — токен-экономика.**

Сравните стоимость discovery:

- **MCP-сервер**: при подключении расходует **тысячи** токенов на список tools/resources. Семь MCP-серверов = десятки тысяч токенов в каждой сессии до того, как ты сказал «привет». Simon Willison оценивает порядок в *«tens of thousands of tokens»*.
- **Skill**: при загрузке списка скиллов модели показывается только `name + description` — обычно **десятки** токенов на штуку. Сто скиллов = пара тысяч токенов на discovery.

В сообществе сильно перекошен фокус на MCP. На Habr и в Reddit обсуждают «какие MCP подключить», в quickstart-гайдах рекомендуют сразу пять-семь штук. Skills упоминаются реже. Это исторически: MCP появился раньше (2024) и стал «фирменным» механизмом расширения. Но **в 2026 году** в большинстве случаев skill дешевле и быстрее, чем эквивалентный MCP. Подключай MCP только когда нужен runtime-доступ (база, GitHub-API, браузер). Для знаний и паттернов — skill.

И возвращаясь к моим 116 скиллам. Из них:

- ~35 я реально вызывал (~30%)
- ~50 имели passive descriptions и были обречены простаивать
- ~30 дублировали друг друга (поставил три варианта TDD-скилла, конкурируют за один триггер)
- ~5 устарели — их репо архивирован

Каждый из этих 81 «мёртвых» скиллов жил у меня в discovery-списке и забирал десятки токенов. На сотне сессий — заметные деньги по Anthropic-API. На бесплатном плане Claude Pro — растущая вероятность «context overflow» в длинных сессиях.

`skill-graveyard` теперь у меня регулярная гигиена. Раз в две недели прогон, чистка мёртвого. Этот процесс — отдельная статья. Здесь важна архитектурная мораль: **skill — это условное правило, и его условие нужно проектировать так же тщательно, как сигнатуру функции.**

## Слой 3. Hooks — гарантия

Hook — это shell-команда (или произвольный исполняемый файл, или HTTP-эндпоинт), которую Claude Code вызывает на определённое событие сессии. Список событий из [официальной доки](https://docs.claude.com/en/docs/claude-code/hooks):

- `PreToolUse` — перед каждым вызовом инструмента (Edit, Write, Bash, MCP-call, etc.)
- `PostToolUse` — после успешного вызова
- `Notification` — когда агент уведомляет пользователя
- `Stop` — когда агент завершил task
- `UserPromptSubmit`, `SessionStart`, `CwdChanged`, `PreCompact` и ещё несколько

Главное свойство hook'а — он работает **всегда**, потому что его запускает не модель, а сам Claude Code как процесс. Модель про hook не знает (если не настроено иначе). Hook возвращает exit code — и тут начинается слой гарантий:

- `exit 0` — всё ок, разрешить операцию
- `exit 1` — мягкая ошибка, агент увидит stderr и решит сам
- `exit 2` — **жёсткий блок**, операция не выполняется, агент получает stderr и идёт думать что делать дальше

Третий вариант — это и есть единственный способ в Claude Code сказать «нельзя» и быть уверенным, что нельзя.

**Hook, который должен быть у каждого. Прямо сейчас:**

```bash
#!/usr/bin/env bash
# .claude/hooks/pre-commit-secrets.sh — block secrets in staged diff
# Привязать к PreToolUse с фильтром по `git commit`.

DIFF=$(git diff --cached 2>/dev/null)

if echo "$DIFF" | grep -qE '(AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{36}|sk-[A-Za-z0-9]{20,}|xox[abp]-[0-9]+-[0-9]+-[0-9]+-[a-f0-9]+)'; then
  echo "Detected secret-like pattern in staged diff. Refusing to commit." >&2
  exit 2
fi
```

Стоит сорок строк, спасает от утечки AWS-key / GitHub PAT / OpenAI key / Slack token — четырёх самых частых источников боли. Агент, который коммитит «чтобы сохранить прогресс», за полминуты успевает закоммитить `.env`, и hook'а никакого нет — потом два часа разговариваешь со службой безопасности.

Можешь сравнить с альтернативой через CLAUDE.md:

```markdown
## БЕЗОПАСНОСТЬ — ВАЖНО!
- НИКОГДА не коммить .env файлы!
- НИКОГДА не пушь secret keys в git!
- ВСЕГДА проверяй staged diff на наличие секретов!
```

На бумаге выглядит надёжно. На практике модель в стрессовой ситуации (ошибка теста, заканчивается контекст, пользователь спешит) **проскочит** это правило в одном случае из ста. Hook не проскочит ни в одном.

**Что ещё полезно как hook:**

- **Запрет `git push --force` в main/production** — на PreToolUse Bash с regex по команде
- **Permission ask на команды со словом `prod` / `production` / `prod-*`** — повышает осознанность
- **JSONL-аудит каждого PostToolUse** — для compliance / разбора инцидентов задним числом
- **Автоформат на PostToolUse Edit/Write** — `prettier --write` / `ruff format` на изменённый файл
- **Уведомления в Telegram/ntfy.sh по Stop** — если запускаешь долгие задачи в фоне

Эмпирическое правило, симметричное правилу для CLAUDE.md: если последствия «модель пропустила правило» серьёзные — это hook, не CLAUDE.md и не skill.

## Архитектурный decision-frame

Когда ставлю задачу настроить поведение агента, прогоняю через таблицу:

| Хочу, чтобы агент… | Слой | Почему |
|---|---|---|
| знал, что проект на Python 3.13 + FastAPI | CLAUDE.md | контекст для лучшего предсказания, последствия нарушения мягкие |
| применял TDD-цикл при добавлении фич | skill | условное правило (нужно только при фичах, не при чтении), есть скилл `mattpocock/skills@tdd` |
| не делал `git push --force` в `main` | hook | последствия катастрофические, нужна гарантия |
| писал тесты в `tests/` рядом с `src/` | CLAUDE.md | мягкое соглашение, нарушение не страшно |
| использовал `pnpm` вместо `npm` | CLAUDE.md или hook | если есть `npm install` в команде — hook на PreToolUse Bash блокирует |
| не редактировал `package.json` без разрешения | hook | важно, проще запретить, чем «попросить» |
| применял мою опинионную методологию ревью | skill | сложная инструкция (40+ строк), не лезет в CLAUDE.md, нужна по требованию |
| прогонял `mypy` после изменения .py файла | hook (PostToolUse Edit) | хочу детерминированно |
| не делал API-вызов в `production.example.com` | hook (PreToolUse Bash + WebFetch) | критично |
| знал, что я работаю с Postgres, а не MySQL | CLAUDE.md | разовая фоновая информация |

Это не догма. Это первичная сортировка — куда положить новое правило. Дальше можно уточнять.

## Curator's gap: где я расхожусь с собственным README

В моём [handbook'е](https://github.com/sfrangulov/claude-code-handbook-ru) в quickstart-разделе написано:

```bash
claude mcp add github
claude mcp add postgres
```

— как «два MCP-сервера ежедневного использования». У меня в `~/.claude/mcp.json` подключён один MCP-сервер: `tolaria` (мой локальный note-taking). Ни GitHub, ни Postgres.

В топ-15 скиллов по install-count из README у меня лидирует `anthropics/skills@frontend-design` (405K установок). Скилл прекрасный — если ты делаешь frontend. У меня 48 скиллов, и большинство — DevOps, MCP-разработка, document-processing, security. Frontend-design стоит, но активируется в одной сессии из двадцати.

Это нормально, и я честно об этом пишу прямо здесь:

**Handbook — это срез того, что работает у среднего читателя в среднем проекте.** Мой setup — это срез того, что работает у меня в моих задачах. Полностью копировать чужой setup — антипаттерн, симметричный «копирую CLAUDE.md от Karpathy». Поэтому в этой статье я не давал список «скачайте 12 скиллов из моего топа». Архитектура важнее инвентаря. Поняв трёхслойку, ты соберёшь свой инвентарь под свои задачи — и он будет работать на тебя, а не на меня.
